Why this strategy
  • Optimize once — tune Memory · Skill · Tool for Claude · Codex · Gemini; from Slack it’s just the native CLI.
  • Fail over providers — PagerDuty tries Gemini → Codex → Claude until one lands.
The hard part — and why I still go this way

The pain lives at the seam

📟

Remote terminal is fragile

Claude Code ships its own remote/web connect. Driving a raw terminal means we own the hard parts:

  • build the askUser bridge (Slack ⇄ provider) ourselves
  • no live stream — Slack shows only the final result
  • tmux polling: detect “done”, auto-confirm, survive restarts
🧩

Every CLI is different

Hooks, launch syntax, confirmation dialogs, “working” indicators — one adapter per provider, maintained forever. Skills have to be tested to work well on every CLI.

🏃

Providers move fast

Hook formats change, Gemini becomes Antigravity — you’re always chasing breaking changes from big tech.

Why not Openclaw or Hermes AI?
  • I don’t want a hard dependency on someone else’s platform.
  • Their updates can break my flow — too risky to build on.
  • I want the native CLI to behave the same whether I run it directly or from Slack — a thin layer, not a rewrite.
Why not build on the Claude Agent SDK?
  • I started there — but on long conversations I hit too many issues I couldn’t resolve.
  • So I came back to the native agent CLI: the providers have already optimized it heavily — I ride that instead of re-solving it.

How EnzoBot works

Monitor & incident response — an agent already on it

PagerDuty alert in Slack→ EnzoBot detects + dedups→ ack PD · react 👀→ auto-start investigation→ post findings · 👀→✅
1Watch — EnzoBot listens to monitored Slack channels for PagerDuty alerts, extracts the incident, and dedups so one alert = one investigation. A burst of alerts is queued and worked one at a time — nothing dropped, nothing run in parallel on the same box.
2Acknowledge — acks the PD incident and drops a 👀 reaction so the team sees it is being handled.
🔐 All SSO / auth-token plumbing for these CLIs is resolved by github.com/lei-wego/wego-infra.
3Investigate — auto-starts a session in tmux from the alert skill + incident permalink (CLI priority Gemini → Codex → Claude, falls through on rate-limit). It pulls real evidence: AWS CLI → Athena order timelines, pup → Datadog APM traces, Sentry CLI → stack traces — and fans out sub-agents that each analyse one source in a clean context.
4Decide & report — before the final report it checks memory (agent-mem) and the partner Slack channel for a known issue, then runs severity logic to call how dangerous it is. Posts findings + verdict to the thread; on resolution swaps 👀 → ✅. The investigation feeds back into memory for next time.

EnzoBot sits on the outside layer — it owns the loop, not the model. It watches the tmux pane to know when the CLI is working, waiting, or stuck — the part we have tuned the most (working indicators, confirmation dialogs, idle detection per CLI). If any provider errors mid-investigation it kills the session, posts a notice, and retries down the CLI chain, so an incident is always re-runnable. A provider going down never means on-call goes dark.

Digging into memory

The agent only gets good if it remembers

1Every step writes to a file — each sub-agent in the loop (brainstorm, plan, build, review, incident…) saves its result to disk. So we can restore from that point, re-investigate a decision, or check the history of how we got here — nothing lives only in one person's head.
2agent-mem — a long-lived Go worker (:34567, Postgres + pgvector, Gemini + Claude Sonnet to distill & embed) that gives every CLI — Claude Code, Codex, Gemini — one shared, persistent memory that syncs across machines.
🧠

Coding-agent memory

CLI hooks stream session-start / prompt / tool-use / stop events to the worker. Gemini distills them into prompts, observations & summaries, embeds into pgvector — so next session recalls relevant context automatically.

🕸️

WEGO memory — graph

A cross-source knowledge graph: Slack · Jira · GitHub · Confluence · PagerDuty · Datadog · Sentry become nodes, references & mentions become typed edges. Ingest runs a job queue (fetch → normalize → extract edges → describe media → embed) — Sonnet extracts the edges & entities (better grounding, fewer hallucinated ids), Gemini embeds & describes media; ask a question and it starts from a seed (a Jira ticket, a Slack thread) and walks outward through the links, ACL-filtered & person-weighted, to assemble one answer — not six tabs.

🧠 Memory from how we actually work

When to reach for it
🆕 New session ↩︎ Resume work 🔁 Hit a bug we’ve seen 🔎 “did we decide this?” → recall, don’t re-explain
Tech design
CLI hooks Go worker :34567 Postgres + pgvector Gemini embed sync_id → cross-machine
How it works
Capturestart · prompt · tool · stop→ Distill Gemini→ Embed pgvector→ Recall hybrid search→ Sync 60s ticker

Why not just a markdown file? You can — Claude Code does, and grep / loading the file into context works fine while it’s small. It breaks at scale: thousands of entries no longer fit in context, and grep only matches exact words (“auth bug” misses “login token expiry”). pgvector ranks by meaning and returns just the relevant top-k within a token budget — plus concurrent hook writes and cross-machine sync. The md file is the thing we outgrew.
